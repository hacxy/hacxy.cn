# 测试驱动开发（Test-Driven Development）

## 理念（Philosophy）

**核心原则**：测试应该通过公开接口验证行为，而不是验证实现细节。代码可以彻底改变，但测试不应该变。

**好测试**是集成风格（integration-style）的：它们通过公开 API 走真实的代码路径。它们描述的是系统**做什么**（_what_），而不是**怎么做**（_how_）。一个好测试读起来像一份规格说明——"用户可以用有效的购物车结账"精确地告诉你系统具备什么能力。这类测试能在重构中存活，因为它们不关心内部结构。

**坏测试**与实现耦合。它们 mock 内部协作对象、测试私有方法，或通过外部手段验证（比如直接查询数据库而不是通过接口）。警告信号：当你重构时测试挂了，但行为并没有变。如果你重命名一个内部函数导致测试失败，那么这些测试测的是实现，而不是行为。

参见 [tests.md](tests.md) 获取示例，[mocking.md](mocking.md) 获取 mock 指南。

## 反模式：水平切片（Horizontal Slices）

**不要先写全部测试，再写全部实现。** 这就是"水平切片"——把 RED 当成"写所有测试"，把 GREEN 当成"写所有代码"。

这会产出**垃圾测试**：

- 批量写出的测试测的是**想象中的**行为，而不是**真实的**行为
- 你最终在测事物的**形态**（数据结构、函数签名），而不是面向用户的行为
- 测试对真实变更不敏感——行为被破坏时它们照样通过，行为正常时反而失败
- 你跑出了自己的头灯照射范围（outrun your headlights），在理解实现之前就锁定了测试结构

**正确做法**：通过曳光弹（tracer bullet）做垂直切片。一个测试 → 一个实现 → 重复。每个测试都回应你从上一个循环中学到的东西。因为你刚写完代码，你确切知道什么行为重要、如何验证它。

```
错误（水平）：
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

正确（垂直）：
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
  ...
```

## 工作流程（Workflow）

### 1. 规划（Planning）

写任何代码之前：

- [ ] 与用户确认需要哪些接口变更
- [ ] 与用户确认要测试哪些行为（排优先级）
- [ ] 找出可以做成[深模块](deep-modules.md)的机会（小接口，深实现）
- [ ] 为[可测试性](interface-design.md)设计接口
- [ ] 列出要测试的行为（不是实现步骤）
- [ ] 让用户批准计划

提问："公开接口应该长什么样？哪些行为最值得测试？"

**你不可能测试所有东西。** 与用户确认到底哪些行为最重要。把测试精力集中在关键路径和复杂逻辑上，而不是每个可能的边界情况。

### 2. 曳光弹（Tracer Bullet）

写一个测试来确认系统的一件事实：

```
RED:   为第一个行为写测试 → 测试失败
GREEN: 写最小代码让它通过 → 测试通过
```

这就是你的曳光弹——证明这条路径端到端可行。

### 3. 增量循环（Incremental Loop）

对剩下的每个行为：

```
RED:   写下一个测试 → 失败
GREEN: 最小代码让它通过 → 通过
```

规则：

- 一次只写一个测试
- 只写足以通过当前测试的代码
- 不要预判未来的测试
- 让测试聚焦于可观察的行为

### 4. 重构（Refactor）

所有测试通过后，寻找[重构候选](refactoring.md)：

- [ ] 提取重复代码
- [ ] 加深模块（把复杂度藏到简单接口后面）
- [ ] 在自然之处应用 SOLID 原则
- [ ] 思考新代码揭示了现有代码的什么问题
- [ ] 每一步重构后运行测试

**绝不在 RED 状态下重构。** 先到 GREEN。

## 每周期检查清单（Checklist Per Cycle）

```
[ ] 测试描述的是行为，不是实现
[ ] 测试只使用公开接口
[ ] 测试能在内部重构后存活
[ ] 代码对当前测试是最小的
[ ] 没有添加投机性的功能
```
