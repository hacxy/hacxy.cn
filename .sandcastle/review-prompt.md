# 审查流程

## 1. 读 diff，找可疑点

仔细读 diff。对任何可疑之处——脆弱逻辑、未检查的假设、棘手的条件、隐式类型转换、缺失守卫——写一个测试来**试图弄坏它**。如果能弄坏，就修。

## 2. 压测边界情况

不止走 happy path。对每个改动的代码路径，思考什么输入或状态会出问题：

- 空数组、空字符串、零、负数
- 缺失可选字段、null、undefined
- 快速重复调用、竞态、运行中状态变化
- 循环或 slice/substring 的 off-by-one
- 相邻功能的回归

为任何未覆盖的路径写测试。

## 3. 代码质量改进

- 减少不必要的复杂度和嵌套
- 消除冗余代码和抽象
- 清晰命名（变量、函数）
- 合并相关逻辑
- 删除重述明显代码的注释
- 避免嵌套三元——优先 switch 或 if/else 链
- 宁显式不取巧——清晰的代码优于过度紧凑的代码

## 4. 保持平衡

避免过度简化带来的问题：

- 降低清晰度或可维护性
- 过度聪明的解法
- 把过多关注点塞进单个函数
- 移除有帮助的抽象

## 5. 保持功能不变

**绝不改变代码"做什么"，只改"怎么做"。** 所有原有特性、输出、行为必须保持完整。只处理本 issue 相关代码，不要顺手改无关代码（同 implement 约束）。

# 执行

1. 先跑 `pnpm run typecheck` 和 `pnpm run test` 确认当前状态是绿的
2. 为原始 bug 写新测试尝试复现——能复现就修
3. 写边界情况测试压测实现
4. 直接在本分支上做代码质量改进
5. 再跑 `pnpm run typecheck` 和 `pnpm run test` 确保没弄坏
6. 用 Conventional Commits 格式提交（`refactor:`/`test:`/`fix:` 等），消息以 `Ralph: Review - <描述>` 开头说明改了什么

如果代码已经干净、测试充分、边界处理到位，什么都不用改，直接进入完成。
